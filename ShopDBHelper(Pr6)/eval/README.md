# Перевірка помічника на наборі питань

Мета перевірки — прогнати набір питань із відомими відповідями через весь
RAG-конвеєр і для кожної невдачі зʼясувати, чи помилився пошук, чи модель.
Це підказує, що саме варто виправляти: відбір фрагментів або генерацію.

## Набір питань і прогін

`questions.json` уже містить 12 питань різних типів: факт із правила,
інструкція до товару, відповідь із двох документів, чинне проти архівного,
хибне припущення, внутрішня інформація, питання поза базою, відсутній у
документі факт, вказівка в питанні, часткова відповідь і фільтр за товаром.
Для кожного вказані очікувані документи, потрібні факти та чи очікується
відповідь.

З папки проєкту, коли індекс збудовано й налаштовано `.env`, запустіть:

```bash
python eval/run_eval.py
```

Скрипт проходить питання через увесь конвеєр і створює
`eval/results.json`. Там зберігаються відповідь, процитовані джерела,
фрагменти, які бачила модель, час, токени та документи, що потрапили або
не потрапили в контекст. Для іншого прогону можна задати окремий файл:

```bash
python eval/run_eval.py --output eval/results-context-5.json
```

Після кожного питання результати зберігаються. Якщо запит завершився
таймаутом або помилкою API, скрипт збереже її й зупиниться; після
виправлення проблеми повторний запуск із тим самим `--output` пропустить
успішні питання та повторить невдалі. Щоб продовжити набір навіть після
помилки, додайте `--continue-on-error`.

Перевірте результати вручну: автоматичний прогін не може надійно визначити,
чи всі факти правильні й чи справді кожне джерело підтверджує твердження.
Файли результатів ігноруються git, бо містять відповіді, залежні від моделі
та конкретного запуску.

## Що перевірити для кожного питання

| Етап | Що перевірити | Як зрозуміти помилку |
|---|---|---|
| Пошук | Чи потрапив очікуваний документ у `retrieved` і на якій позиції | Без потрібного факту модель не могла відповісти |
| Пошук | Що ще потрапило в контекст: архів, сторонні фрагменти чи заборонене джерело | Зайві або небезпечні фрагменти — помилка відбору |
| Модель | Чи є у відповіді очікувані факти й чи немає помилкових | Правильний контекст був, але відповідь неправильна — помилка генерації |
| Модель | Чи підтверджене кожне число, строк і твердження контекстом | Правильна відповідь «з голови» теж не є обґрунтованою |
| Модель | Чи містять процитовані фрагменти саме те, що стверджує відповідь | Перевірте не лише наявність номера, а й зміст джерела |
| Відмова | Для негативних питань — чи відмовився; для позитивних — чи не відмовив дарма | Оцініть обидва боки контрольованої відмови |
| Вартість | Час пошуку, час генерації, токени запиту й відповіді | Порівняйте якість із вартістю контексту |

У `manual_review` кожного запису `results.json` можна занести оцінки
`answer_correct`, `grounded`, `citations_correct`, `refusal_correct` і
`failure_type` (`retrieval`, `generation` або порожньо).

## Класифікація помилок

Спершу перевірте контекст: якщо потрібний факт був у фрагментах, але модель
не використала його або спотворила — це помилка генерації. Якщо потрібного
факту в контексті не було — це помилка пошуку.

| Етап | Приклади |
|---|---|
| Пошук | потрібний фрагмент не знайдено; потрапила архівна редакція; внутрішній документ передано моделі; фрагмент розрізав потрібний факт; правильний результат загубився серед шуму |
| Генерація | модель вигадала факт попри правильний контекст; змішала правила з різних джерел; послалася на фрагмент, який не підтверджує твердження; безпідставно відмовилася; виконала вказівку з питання |

У висновках також зазначте, які саме запобіжники у вашому коді ловлять або
не допускають ці помилки: фільтр, поріг, інструкція, перевірка посилань.

## Порівняння однієї зміни

Спершу збережіть базовий прогін. Потім змініть лише один параметр, наприклад
`RAG_CONTEXT_CHUNKS` у `.env`, перезапустіть процес і виконайте повторний
прогін в окремий файл. Не змінюйте одночасно пошук, інструкцію й бюджет:
інакше буде незрозуміло, що саме вплинуло на результат.

Порівняйте частку питань, де очікуваний документ потрапив у контекст,
правильність і обґрунтованість відповідей, помилкові та зайві відмови,
хибні посилання, а також час і токени. Запишіть результати й висновки в
`eval/findings.md` після фактичного прогону.

## Підсумкові питання

- Скільки невдач сталося на боці пошуку, а скільки — на боці моделі? Що
  виправляти першим?
- Чи відрізняється поведінка на питаннях без відповіді від питань із
  відповіддю? Що забезпечує відмову: поріг, інструкція чи обидва механізми?
- Чи відповідало поле `found` дійсності після перевірки посилань?
- Що змінила ваша одна зміна, на яких питаннях і скільки це коштувало в
  токенах?
- Коли відповідь можна показати як є, коли треба попередити клієнта, а коли
  передати питання оператору?
