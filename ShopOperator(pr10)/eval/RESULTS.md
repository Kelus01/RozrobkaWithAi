# Результати перевірки ПР10

## Умови

- Локальна перевірка виконувалась на Python 3.12 із `LLM_PROVIDER=mock`, без API-ключа і без запитів до зовнішньої моделі.
- `python3 -m unittest discover -s tests -v`: **28 тестів пройшли**.
- `LLM_PROVIDER=mock python3 check_env.py`: середовище готове, усі 8 зразків читаються, незавершених реалізацій не знайдено.
- Pylance workspace diagnostics: помилок і попереджень немає; синтаксис перевірено для 13 Python-файлів.
- У браузері вручну перевірено створення `d01`, потокове заповнення, кінцевий статус, відображення провайдера й часу. Вимір одного локального запуску: перший фрагмент через **0,606 с**, завершення через **1,394 с**, 233 mock-токени. Це вимір mock, не справжньої моделі.
- У браузері також перевірено редагування чернетки: повтор показує підтвердження, а відмова від повтору зберігає текст правки.

## Сценарії, покриті автоматичними перевірками

| Сценарій | Результат |
|---|---|
| Звичайна чернетка, mock без ключа, події `queued` → `running` → `delta` → `done` | Пройдено; SSE endpoint відтворює завершені події |
| Таймаут спроби, таймаут бездіяльності після першого фрагмента, загальний бюджет | Пройдено; кожен завершується контрольованим `timeout` у заданих межах |
| Тимчасовий збій, повтор із паузою, скидання часткового тексту | Пройдено; повторна спроба починається з чистого тексту |
| Постійна недоступність і невідновлювана помилка доступу | Пройдено; кількість спроб обмежена, `auth` не повторюється |
| Mock-збої `timeout`, `rate_limit`, `unavailable`, `auth`, `bad_request`, `mid_stream` | Пройдено; тип і ознака повторюваності перевіряються |
| `Retry-After` у межах бюджету та довший за бюджет | Пройдено; короткий інтервал витримується, довгий не очікується і не запускає fallback |
| Fallback після збою основного провайдера | Пройдено; результат позначається як fallback |
| Обмеження одночасності | Пройдено; при зайнятих слотах застосунок відмовляє одразу, без прихованого очікування |
| Скасування під час роботи, під час backoff і після завершення | Пройдено; скасована чернетка не стає `done`, повторне скасування завершеної повертає 409 |
| Неочікуваний виняток у фоновій роботі | Пройдено; чернетка переходить у `failed`, користувач не отримує текст внутрішнього винятку |
| 400/404/409/429, єдина структура помилки й `Retry-After` | Пройдено |
| Пʼять одночасних запитів | Пройдено з тестовим лімітом 3: прийнято 3, два відхилено з 429 |
| Збереження подій для повторного відкриття чернетки | Пройдено через SSE replay та endpoint після завершення |
| Перевірка критичних номерів у тексті | Пройдено; валідна відповідь `d01` не отримує зайвого попередження про рік у даті |

## Рішення та висновки

- Таймаути за замовчуванням залишені з `.env.example`: 20 с на спробу, 8 с без фрагмента, 45 с на весь запит. Локальний mock завершив приклад за 1,394 с, але ці значення не вважаються вимірюванням продуктивності справжньої моделі.
- Повторюються лише помилки з `retryable=True`. Пауза експоненційна з jitter; `Retry-After` має перевагу. Якщо інтервал не вміщується в бюджет, застосунок не чекає і не робить додатковий виклик до fallback.
- Якщо частина відповіді вже була показана, перед retry/fallback надсилається статус `reset`, а поле очищається. Якщо спроби вичерпано без успіху, останній частковий текст лишається видимим поруч із помилкою.
- Fallback викликається один раз після невдачі основного провайдера й позначається в статусі та результаті. Mock призначений для локальної розробки/перевірки, а не для непомітної заміни відповіді в робочому середовищі.
- Обмеження одночасності відмовляє одразу з повторюваною помилкою замість мовчазної черги. Ліміт клієнта — ковзне 60-секундне вікно; відхилені спроби не додаються до вікна, прийняті замовлення рахуються і після подальшого збою чи скасування.
- Реєстр і журнал подій у памʼяті процесу; зберігається до 100 завершених чернеток. Перезапуск процесу очищує стан, тому для довготривалого production-сервісу потрібне зовнішнє сховище.
