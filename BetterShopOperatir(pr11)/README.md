# ПР10–11. Надійність, спостережуваність і контроль витрат AI-сервісу

Розширення застосунку ПР10 для практичної роботи №11. Повний текст вимог ПР10 і критерії приймання наведені в `ПР10.pdf`; вимоги ПР11 — у виданому окремо документі `ПР11.pdf`.

## Задача коротко

Оператор підтримки «Сузірʼя» відповідає на звернення клієнтів. Факти — номер заявки, строки, куди привезти товар — він уже встановив (у ПР9 це робив workflow); лишилося написати відповідь людською мовою. Модель складає **чернетку**, оператор її редагує й надсилає.

Один виклик моделі ви робили ще в ПР3. Тепер цей виклик стоїть у застосунку, яким користуються весь день: провайдер відповідає по 10–20 секунд, іноді повертає 429 або 5xx, ключ може протермінуватися, а оператор, який не бачить, що відбувається, натискає кнопку ще раз. Тому в цій роботі модель — не головне. Головне — усе, що між HTTP-ендпоінтом і моделлю: **абстракція провайдера**, **таймаути**, **обмежені повторні спроби**, **контрольовані помилки**, **обмеження частоти**, **фонова генерація з потоком фрагментів**, **скасування** і **підставний провайдер**, з яким усе це можна перевірити без ключа.


Застосунок генерує чернетки у фоновому режимі й відтворює стани та фрагменти через SSE. Сторінка показує чергу, спроби, провайдера, запасний варіант і час до першого фрагмента; текст можна редагувати, скасувати генерацію, скопіювати чернетку або замовити повтор. Для локального запуску без ключа задайте `LLM_PROVIDER=mock`.

## Початок роботи

1. **Середовище:**

   ```bash
   python -m venv .venv
   .venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   copy .env.example .env
   ```

   Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`. Ключ доступу перенесіть у `.env` з папки попередньої роботи.
   На macOS/Linux команди запуску Python нижче використовують `python3` (команда `python` може бути не встановлена).

2. **Перевірка:**

   ```bash
   python3 check_env.py
   ```

   Запустіть заздалегідь. Скрипт зробить пробний запит у режимі streaming і покаже, через скільки прийшов перший фрагмент і скільки тривала відповідь, — від цих чисел відштовхуйтеся, обираючи таймаути. Якщо запит провалився, скрипт назве вид збою — той самий, який має розрізняти ваш провайдер.

Запуск застосунку з папки `pr10`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000. Для роботи без ключа в `.env` задайте `LLM_PROVIDER=mock`; для справжнього провайдера заповніть `LLM_API_KEY`. Реєстр зберігається в памʼяті процесу, тож `--reload` чи перезапуск очищає чернетки.

Ідентифікатор `client` у цій навчальній сторінці зберігається в `sessionStorage` лише для демонстрації ліміту. У розгорнутому сервісі його потрібно брати з перевіреної серверної сесії, а не довіряти значенню з тіла запиту.

Фокусні автоматизовані перевірки запускаються командою `python3 -m unittest discover -s tests` на macOS/Linux (`python -m unittest discover -s tests` на Windows). Вони використовують підставний провайдер і не потребують ключа.

Для вимірювання справжнього провайдера після налаштування ключа в `.env` див. інструкції в [`eval/README.md`](eval/README.md). Цей benchmark надсилає оплачувані зовнішні запити; dry-run та локальні тести API не викликають.

## ПР11: спостережуваність і бюджет

Кожен HTTP-запит отримує `X-Request-ID`. За ним і `draft_id` можна зібрати події чернетки у `logs/app.jsonl`; журнал містить метадані, тривалості, токени й вартість, але не ключ, текст звернення чи prompt. Локальні логи, кеш і бюджет пишуться в `logs/` та `state/`, виключені з git.

У `.env.example` додані ціни за мільйон токенів, денний ліміт, поріг попередження й налаштування TTL/файлів кешу. Ціни є прикладом — звірте ставки зі сторінкою провайдера. `/api/health` показує залишок бюджету та стан кешу; завершена чернетка показує свою вартість і чи була відповідь з кешу. Повтор через «Повторити» передає `fresh=true` і обходить кеш.

Аналіз журналу:

```bash
python3 eval/analyze.py --log logs/app.jsonl --slow-seconds 10
```

Для контрольованого порівняння одного потоку з повторами див. replay інструкції в [`eval/README.md`](eval/README.md). Replay робить API-виклики й може витрачати квоту/бюджет; запускайте його лише на `LLM_PROVIDER=mock` або свідомо погодивши реальні витрати.

## Що очікує сторінка

Замовлення чернетки — `POST /api/drafts` з `{"request_id": "d01", "client": "…"}`; у відповідь — знімок чернетки: `draft_id`, `status`, `text`, `attempts`, `provider`, `model`, `fallback`, `error`, `usage`, `elapsed`, `warnings`. Помилки мають спільний формат `{"error": {"kind": "…", "message": "…", "retryable": …, "request_id": "…"}}`; для обмеження частоти додається заголовок `Retry-After`.

Далі сторінка відкриває `GET /api/drafts/{id}/events` і розуміє події `status`, `delta`, `done`, `error`, `cancelled` (їхні поля описано в `app/jobs.py`); інші показує в журналі як є. Статуси чернетки: `queued`, `running`, `done`, `failed`, `cancelled`. Скасування — `POST /api/drafts/{id}/cancel`; перелік — `GET /api/drafts`; знімок — `GET /api/drafts/{id}`; налаштування для шапки — `GET /api/health`.

## Реалізовані механізми

| Рівень | Реалізація |
|---|---|
| Провайдери | Єдиний контракт; SDK-винятки нормалізуються; mock працює без мережі |
| Шлюз | Три бюджети часу, обмежені повтори з jitter, semaphore без прихованої черги, fallback після primary |
| Фонова робота | SSE-події з відтворенням, скасування через `threading.Event`, кінцевий статус навіть після неочікуваної помилки |
| Веб-рівень | Єдина форма помилки; 400/404/409/429; `Retry-After` на відмову ліміту |
| Чернетка | Тільки перевірені факти в системній інструкції; коди лише попереджають, не блокують оператора |
| `eval/` | Сценарії та фактичні результати локальних перевірок у `eval/RESULTS.md` |

Вибір деталей для відтворення в локальних сценаріях і фактичні результати наведені в `eval/RESULTS.md`.
